# データベース設計方針（第2版）

`schema.sql` を実際にPostgreSQL 16へ投入し、得意先→商品→売上伝票→明細という一連の登録・参照ができることを確認済みです（テーブル数40）。

第2版では、実際にお預かりした旧システム（`hanbai`）のデータ一式（得意先マスタ92件、仕入先マスタ83件、商品マスタ145,833件、売上伝票472件／明細845件、仕入伝票2,533行、請求書・納品書の実物イメージ）を使って設計を検証し、見つかった差分をスキーマに反映しました。検証はこのデータをPostgreSQLへ実際にINSERTする形で行い、得意先・仕入先・商品は全件、売上伝票は現金売上を除く444/472件（理由は下記）が制約エラーなく登録できることを確認しています。

## 設計のポイント

現行システムの画面から読み取った項目はほぼそのまま踏襲し、テーブル名・列名は保守性を考えて英語のsnake_caseにしています（列コメントで旧システムの項目名と対応させています）。主な設計判断は次の通りです。

売上伝票と現金売上伝票は、旧システムでは別画面でしたが得意先を「現金売上」用の固定コードに向ける以外に構造の違いがないため、`sales_vouchers`テーブルに`is_cash_sale`フラグを持たせて1つにまとめました。運用上どうしても分けて集計したい場合はフラグで絞り込めます。

消費税率は`tax_rate_history`で開始日ごとに履歴管理し、各伝票には起票時点の税率を`tax_rate`列にスナップショットとして保存します。後から税率が変わっても過去伝票の税額が変わらないようにするためです。

請求処理は「都度計算して都度表示する」のではなく、旧システムの「請求更新」という締め処理の考え方をそのまま残し、`billing_closings`（締め処理の実行履歴）と`billing_records`（得意先ごとの確定した請求実績）に分けています。締め後に金額を直接修正できる「請求実績修正」画面もこの`billing_records`を編集する形で再現できます。仕入・支払側も同じ構造（`payment_closings` / `payment_records`）です。

見積書入力（階層）は、明細行に`level`という見出しレベルの列を持たせることで、通常の見積とテーブル構造を共通化しました（`level=0`が通常の明細行、1以上が中見出し行という想定）。

在庫は商品マスターに現在の在庫数量・在庫金額（移動平均単価）を持たせつつ、`inventory_movements`に全ての出入りを1件ずつ記録します。これにより「商品受払台帳」のような時系列の在庫推移レポートも作れます。

プリンター関連の設定（伝票トレイ、印字位置の微調整など）は、白紙にレイアウトごと印刷する方針に変更したため、新しいスキーマには含めていません。

## 確認済み事項（ご回答いただいた内容）

売上単価①〜⑤と得意先の「売上単価ランク」は、ランク＝単価の番号という理解で問題ないとのことでした。ただし社内では実際には使っていない機能とのことなので、`price_rank`列はスキーマ上は残しつつ、画面実装の優先度は下げます。

得意先の「請求先コード」（`billing_customer_code`）は、グループ会社等の請求をまとめる仕組みという理解で正しいとのことでした。設計そのまま採用します。

## 第2版で追加・変更した項目（実データ検証で判明）

実データを流し込んで初めて分かった、旧システムにはあるが第1版のスキーマに無かった項目・設計ミスです。

- **商品名・得意先名のあいまい検索**：商品マスタが14万件超と大規模なため、`pg_trgm`拡張を有効化し、`idx_products_name_trgm` / `idx_customers_name_trgm` を通常のB-treeインデックスからGINのトライグラムインデックスに変更しました（第1版は名前だけ`trgm`と付いていて実体は普通の索引でした）。
- **売上伝票の入力日付**：売上伝票CSVに「伝票日付」とは別に「入力日付」の列があり、実運用では両者がずれることがあるようだったので、`sales_vouchers.entered_on`として追加しました。
- **売上伝票明細の明細消費税・備考2**：明細CSVに、伝票側の消費税とは別に明細ごとの消費税額（`明細消費税`）と、備考欄が2つ（`備考`・`備考2`）存在することが分かったため、`sales_voucher_lines`に`tax_amount`と`note2`を追加しました。値引き行（例：「出精値引」を数量-1・金額マイナスで入力）もそのまま登録できることを確認済みです。
- **銀行マスタの支店・口座情報**：実物の請求書に「北國銀行森本支店（普）170498」のように支店名・口座種別・口座番号が印字されていましたが、`banks`テーブルには銀行名しかなかったため、`branch_name`・`account_type`・`account_number`・`account_holder`を追加しました。
- **会社情報（インボイス登録番号など）**：実物の請求書に自社の適格請求書発行事業者登録番号（T+13桁）・住所・電話・FAXが印字されていましたが、`company_settings`には会社名しかなかったため、`postal_code`・`address1`・`address2`・`phone`・`fax`・`invoice_registration_no`を追加しました。

## 検証時に判明した運用上の注意点（スキーマとは別の話）

- CSVエクスポートでは、得意先コード・商品コードなどの数値だけのコードがExcelの書式によって先頭ゼロが落ちる場合があります（例：売上伝票側の得意先コードが`66`となっていて、マスタ側の`0066`と一致しない）。将来CSV取り込み機能を作る際は、コード列を必ずゼロ埋めして突き合わせる処理が必要です。
- 売上伝票のうち28件は得意先コード`0001`を参照していましたが、今回いただいた得意先マスタには含まれていませんでした。おそらく現金売上用の固定得意先（`company_settings.cash_customer_code`に相当）と思われますが、今回のマスタ抽出範囲に含まれていなかっただけの可能性が高いです。実運用データで存在を確認したいです。
- 商品マスタの「分類区分1〜3」「中分類・小分類コード」は、14万件中ほぼ全件が同一の値（実質未使用）でした。列自体は残しますが、画面実装では大分類コードのみ優先し、他は後回しにするのが良さそうです。

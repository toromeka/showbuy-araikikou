# 荒井機工 販売管理システム（アプリ）

Next.js（App Router）+ TypeScript + Prisma + Auth.js（NextAuth v5, Credentials認証）構成の業務アプリです。
データベース設計そのものは一つ上の階層の `schema.sql` / `README.md`（DB設計方針）を参照してください。

現時点で実装済みなのは、マスタ管理画面（得意先・仕入先・商品。一覧検索（`pg_trgm`によるあいまい検索対応）・新規登録・編集・無効化（論理削除）・CSV取り込み）、売上伝票・仕入伝票・入金伝票・支払伝票・見積書の入力画面（いずれも新規登録・編集・削除・一覧検索）、請求更新（締め処理）・仕入支払更新、商品受払台帳、そして各種帳票（請求書・納品書・見積書）のPDF出力です。

## 売上伝票について

- 一覧画面（`/sales-vouchers`）から新規登録・検索（伝票番号・得意先コード・得意先名・日付範囲）ができます
- 明細行は商品コード・商品名の部分一致（あいまい検索対応）で商品マスタから検索し選択できます。商品マスタに無い品名（値引きなど）は自由入力も可能です
- 数量はマイナス値を許容します（値引き・返品行なども1明細として表現できます）
- 消費税率は伝票日付をもとに `tax_rate_history` から自動判定されます（現行は2019/10/1以降10%）
- 金額の丸め方式は得意先マスタの `rounding_method`（四捨五入・切捨て・切上げ）に従います
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `sales`）
- 請求確定済み（`is_billed = true`）の伝票は編集・削除できません

## 仕入伝票について

- 一覧画面（`/purchase-vouchers`）から新規登録・検索（伝票番号・仕入先コード・仕入先名・日付範囲）ができます
- 明細の商品検索・自由入力・マイナス数量（返品など）は売上伝票と同様に使えます
- 売上伝票と異なり、明細は仕入単価・仕入金額のみです（売価は扱いません）。伝票全体では仕入金額（`subtotal_amount`）・消費税額・合計金額を管理します
- 消費税率・丸め方式の判定ロジックは売上伝票と共通です（丸め方式は仕入先マスタの `rounding_method` を参照）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `purchase`。売上伝票とは別の連番です）
- 支払更新済み（`is_settled = true`）の伝票は編集・削除できません

## 入金伝票について

- 一覧画面（`/receipt-vouchers`）から新規登録・検索（伝票番号・得意先コード・得意先名・日付範囲）ができます
- 入金明細は1伝票に複数行登録でき、行ごとに区分（現金・振込・手形・その他）と金額を入力します
- 区分が「振込」「手形」の行は振込先銀行（銀行マスタ `banks` から選択）を指定できます。「手形」の行はさらに手形決済日・手形Noを入力できます
- 請求金額・売上金額・消費税額は、請求更新（締め処理）が未実装のため、現時点では参考情報として手入力する項目です（旧システムの請求書と照合する際の控えとして利用してください）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `receipt`）
- 売上伝票・仕入伝票と異なり「確定状態」を表すフラグがスキーマ上存在しないため、入金伝票はいつでも編集・削除できます

## 支払伝票について

- 一覧画面（`/payment-vouchers`）から新規登録・検索（伝票番号・仕入先コード・仕入先名・日付範囲）ができます
- 入金伝票と同じ構成です（対象が得意先→仕入先に変わり、参考項目が「売上金額」→「仕入金額」になります）。区分（現金・振込・手形・その他）ごとに明細行を登録し、「振込」「手形」は支払元銀行を、「手形」はさらに手形決済日を指定できます
- 入金伝票の `bill_no`（手形No）に相当する項目はスキーマ上支払伝票には無いため、支払伝票の明細には手形Noの入力欄がありません
- 請求金額・仕入金額・消費税額は、請求更新（締め処理）が未実装のため参考情報として手入力する項目です
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `payment`）
- 入金伝票と同様、確定状態のフラグがないためいつでも編集・削除できます

## 見積書について

- 一覧画面（`/quotations`）から新規登録・検索（伝票番号・得意先コード・得意先名・案件名・見積日範囲）ができます
- ヘッダには案件名（2行）・納期・受渡場所・荷造運賃・支払条件・有効期限・参照番号・補助番号・相手先担当など、旧システムの見積書帳票に合わせた項目を用意しています
- 「階層タイプ」チェックボックスを入れると、明細行ごとに「明細行／見出し（大・中・小）」を選べるようになります。見出し行は品名テキストのみを持ち、金額の集計には含まれません（インデント表示されます）。チェックを外すと通常の明細のみの見積書になります
- 明細の商品検索は売上伝票・仕入伝票と同じ仕組みで、商品マスタに無い品名の自由入力にも対応しています
- 見積金額・原価金額・粗利額は明細行（見出し行を除く）の数量×単価から自動計算されます
- 「消費税を含めて計算する」はスキーマ上フラグのみを保持する項目で、実際の消費税額は計算・保存されません（旧システムの仕様を踏襲した表示用の設定です）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `quotation`）。確定状態のフラグはないためいつでも編集・削除できます
- `quotation_lines.category`（区分）列は現状フォームに出していません（用途が明確になり次第、他マスタ同様に追加予定です）

## 請求更新（締め処理）について

売上伝票をもとに得意先ごとの請求額を確定させる処理です。旧システムの「請求更新」に相当します。

- `/billing-closings` から「新規実行」を選び、締日（5日・10日・15日・20日・25日・月末、またはすべての締日）と基準日（この日までの伝票を集計）を指定して「プレビュー」すると、対象になる得意先と金額の内訳が実行前に確認できます。内容を確認したうえで「この内容で請求更新を実行する」を押すと確定します
- 対象は、得意先マスタの「締日」（未設定の場合は会社設定の既定締日）が指定した締日と一致する得意先です。得意先の「請求先コード」で請求がまとめられている場合は、まとめ先の得意先の1件としてグループ集計されます（グループ内の各社の売上・入金を合算）
- 金額の計算式は「今回請求額 = 前回請求残 + 今回売上金額 + 消費税額 − 今回入金額」です。前回請求残は前回の請求更新（取り消されていないもの）の請求額を、それが無い場合は得意先マスタの「稼動時残高」を初期値として使います
- 今回売上金額の対象は、まだ請求更新されていない（`is_billed = false`）売上伝票のうち伝票日付が基準日以前のものすべてです。今回入金額の対象は、前回の請求更新の集計期間の翌日から基準日までに登録された入金伝票です
- 実行すると、対象の売上伝票はすべて「請求確定済み」（`is_billed = true`）になり、編集・削除ができなくなります
- 実行履歴は一覧・詳細画面でいつでも確認できます。詳細画面の「この請求更新を取り消す」から取り消すと、対象の売上伝票は「未請求」に戻り、以後の請求更新で再度対象になります（取り消した履歴はレコードとして残ります）
- 対応するのは売上・請求（得意先向け）です。仕入・支払（仕入先向け）は「仕入支払更新」として別に用意しています

## 仕入支払更新について

仕入伝票をもとに仕入先ごとの支払額を確定させる処理です。旧システムの「仕入支払更新」に相当し、請求更新（得意先向け）と対になる仕組みです。

- `/payment-closings` から「新規実行」を選び、締日と基準日を指定して「プレビュー」すると、対象になる仕入先と金額の内訳が実行前に確認できます。内容を確認したうえで「この内容で仕入支払更新を実行する」を押すと確定します
- 対象は、仕入先マスタの「締日」（未設定の場合は会社設定の既定締日）が指定した締日と一致する仕入先です。得意先の「請求先コード」のような請求先グループ化の仕組みは仕入先マスタには無いため、仕入先ごとに個別に集計されます
- 金額の計算式は「今回支払額 = 前回残高 + 今回仕入金額 + 消費税額 − 今回支払額（支払伝票分）」です。前回残高は前回の仕入支払更新（取り消されていないもの）の支払額を、それが無い場合は仕入先マスタの「稼動時残高」を初期値として使います
- 今回仕入金額の対象は、まだ仕入支払更新されていない（`is_settled = false`）仕入伝票のうち伝票日付が基準日以前のものすべてです。今回支払額（相殺分）の対象は、前回の仕入支払更新の集計期間の翌日から基準日までに登録された支払伝票です
- 実行すると、対象の仕入伝票はすべて「支払更新済み」（`is_settled = true`）になり、編集・削除ができなくなります
- 実行履歴は一覧・詳細画面でいつでも確認できます。詳細画面の「この仕入支払更新を取り消す」から取り消すと、対象の仕入伝票は「未払」に戻ります（取り消した履歴はレコードとして残ります）

## 商品受払台帳について

商品ごとの入庫（仕入）・出庫（売上）の履歴と残数量・残高金額を確認できるレポート画面です。

- `/inventory-ledger` を開くと商品検索欄が表示されます。商品マスタは約14万6千件あるため、コードまたは商品名で絞り込んでから選択します
- 商品を選ぶと、その商品の売上伝票・仕入伝票の明細を日付順に並べた受払台帳が表示されます。期間（From/To）で絞り込むこともできます。期間のFromを指定した場合、それより前の全履歴を集計した「前期繰越」を先頭行に表示します
- 数量は仕入伝票の明細を入庫、売上伝票の明細を出庫として扱い、残数量は入庫−出庫の累計です。残高金額は仕入原価（`cost_amount`）ベースの累計です（売価ではなく原価で評価する、一般的な受払台帳の考え方です）
- スキーマ上の `inventory_movements` テーブル（受払ログ用）は現在使用していません。この画面は売上伝票・仕入伝票の明細から都度計算する方式のため、伝票を修正・削除すれば台帳の内容も自動的に反映されます
- 商品マスタの `stock_qty`（在庫数量）・`stock_amount`（在庫金額）は画面上部に参考表示していますが、旧システムからの移行時点で在庫数量が引き継がれていないため通常0のままです。この受払台帳の残高計算とは連動しません
- 対象は商品コードが明細に記録されている行のみです。値引き・自由入力行など商品コードの無い明細は集計対象外です

## 各種帳票（PDF出力）について

売上伝票・見積書・請求更新の実績それぞれの詳細画面に「〜PDF」ボタンがあり、クリックすると別タブでPDFが開きます（`Content-Disposition: inline`）。

- **納品書**（`/sales-vouchers/[id]/print`）: 売上伝票の明細から生成します。顧客向け帳票のため、仕入原価・粗利など内部情報は含みません。実物の複写伝票を模して、A4用紙1枚の上半分に「納品書」・下半分に「納品書（控）」を同一内容で印刷するスタイルです。明細は1枚（正・控とも）につき最大7品番までで、8品番目以降がある場合は同じ伝票番号のまま2枚目以降の用紙に続きが出力されます（例: 9品番なら1枚目に1〜7品番目、2枚目に8〜9品番目）。小計・消費税・合計は最終ページのみに記載し、途中のページには「次ページに続く」旨の注記を表示します。日付・得意先コード・伝票番号のミニボックス、項番＋商品名／規格を1セルにまとめた列構成、破線罫線、[摘要][小計][消費税][合計]を横並びにした集計バーなど、細部のレイアウトは、以前ユーザーがFlutterで試作していた `invoice_pdf_generator.dart`（自社の実際の納品書フォーマットに合わせて作られたもの）を参照して再現しています。ただし「7品番を超える場合の複数枚出力」はその試作版になかった機能で、今回新規に追加しました
- **見積書**（`/quotations/[id]/print`）: 見積書の明細から生成します。階層タイプの見出し行にも対応しています。同じく原価・粗利は含みません。`tax_calculated`（税込で計算したか）フラグは quotations テーブルに税率が保存されていないため、税額を別途計算せず「上記金額は消費税を含めて（含めずに）計算しています」という注記のみ表示します
- **請求書**（`/billing-closings/[id]/records/[recordId]/print`）: 請求更新の実績（`billing_records`）1件から生成します。「今回売上明細」は、その請求グループ（請求先に紐づく子アカウントも含む）に属し、かつその実績の対象期間（`period_from`〜`period_to`）に該当する売上伝票を都度再集計したものです。これは請求更新の取り消し処理が対象伝票を再特定するのに使っているのと同じ絞り込み条件なので、中間テーブルを持たずに「この請求に何が含まれていたか」を後から正確に再現できます
- 会社情報（自社名・住所・電話・FAX・適格請求書発行事業者登録番号）は `company_settings` テーブルから、振込先情報は `banks` テーブルの `is_own_company = true` の行から取得して各PDFに印字します（振込先が未登録の場合は単に非表示になります）
- 得意先名のあとの敬称は、`customers.honorific` が数値コードで意味の対応表がスキーマ上どこにもない（既存のマスタ画面でも生の値をそのまま表示しているだけ）ため、PDFでは一律「御中」を付けています。実際の敬称ルールと異なる場合は個別に見直してください
- PDF生成は、サーバー上でPlaywright（Chromium）を都度起動してHTMLを印刷する方式です。日本語フォント（Noto Sans CJK）が入っている環境が前提のため、本番環境に配置する際は `npx playwright install chromium` を実行してブラウザ本体を用意してください（`package.json` の `dependencies` に `playwright` を含めています）

## 同時アクセス（複数端末からの同時利用）について

複数のPCから同時にログインして同時にデータを処理するケースを想定し、以下の対策をしています。

- **セッション**: Auth.jsはJWTセッション（サーバー側にセッションストアを持たない方式）なので、複数端末からの同時ログインはそもそも制約なく動作します
- **伝票番号の採番**: `voucher_sequences` テーブルへの採番はDBトランザクション内の原子的なUPDATE（`increment`）で行っており、PostgreSQLの行ロックにより同時に採番しても重複しません（さらに`voucher_no`列にUNIQUE制約があるため、万一の場合もDBレベルで重複が拒否されます）。5端末から同時に伝票を登録して番号が重複しないことをスモークテストで確認済みです
- **伝票番号が衝突した場合の自動繰り上げ**: 旧システムでは、他端末との競合で番号が衝突しそうな場合は自動的に次の番号へ送って登録・印刷を継続する挙動だったとのことなので、同様の動きにしています。データ移行直後の採番カウンタと実データのズレや、手作業でのDB調整などにより、採番した番号がたまたま既存の伝票番号と衝突した場合、エラー画面を出さずに自動的に次の番号を採番し直して保存を続行します（`src/lib/voucher-number.ts` の `withVoucherNoRetry`、最大5回まで自動リトライ）。売上伝票・仕入伝票・入金伝票・支払伝票・見積書のすべての新規登録に適用しています。実装上の注意点として、採番のincrement処理は伝票本体の保存とは別にコミットするようにしています（同じDBトランザクションにまとめてしまうと、保存側が失敗した際にincrementまで巻き戻り、リトライしても同じ番号に衝突し続けてしまうため）。`scripts/smoke_voucher_number_retry.mjs` で、あらかじめ次の番号を使う伝票を仕込んだ状態から新規登録しても、その次の番号で自動的に登録が完了することを確認しています
- **採番カウンタと実データの同期**: 今回のデータ移行時点で `voucher_sequences`（売上伝票）のカウンタが実データの最大伝票番号より大幅に低い状態（カウンタ54に対し実データ最大144870）だったため、`scripts/sync_voucher_sequences.mjs` を実行し、各伝票種別のカウンタを実データの最大値まで引き上げました。このスクリプトは「カウンタが実データの最大値より小さい場合のみ引き上げる」という冪等な処理なので、何度実行しても安全です。将来、本番データへの本格的なカットオーバーを行う際は、同じスクリプトをもう一度実行してください（`node scripts/sync_voucher_sequences.mjs`）
- **請求更新・仕入支払更新の二重実行防止**: 「未請求（未払）データを集計→実績を作成→対象伝票を確定済みにする」処理はDBトランザクションでまとめていますが、PostgreSQLの既定の分離レベル（READ COMMITTED）では、2人がほぼ同時に「実行」を押すと同じ未処理データを両方が読んでしまい、二重請求・二重支払処理が起こり得ます。これを防ぐため、実行・取り消しのトランザクション冒頭で `pg_try_advisory_xact_lock` によるロックを取得し、同じ種類の締め処理はクラスタ全体で常に1件ずつ順番に処理されるようにしています。ロックが取得できなかった場合は「他の端末で同じ種類の締め処理を実行中です。少し待ってから、もう一度お試しください。」というエラーになります（`src/lib/closing-lock.ts`）
- **請求確定済み・支払確定済み伝票の編集/削除防止（TOCTOU対策）**: 伝票の編集・削除は、事前に確定状態を確認したうえで実行しますが、その確認と実際の更新/削除の間に別端末で請求更新・仕入支払更新が割り込む可能性があります。これを防ぐため、実際の更新・削除処理そのものに `is_billed: false` / `is_settled: false` の条件を含め、「未確定であることの確認」と「更新・削除」を1つの原子的なSQL文にまとめています。競合していた場合は「請求確定済みの伝票は編集できません（他の端末で先に請求更新された可能性があります）。」のようなエラーになります
- **DB接続プール**: 複数端末からの同時アクセスを想定し、`src/lib/prisma.ts` でPostgreSQL接続プールの上限を明示的に設定しています（既定20、`DATABASE_POOL_MAX` 環境変数で変更可能）
- これらは `scripts/smoke_concurrency.mjs` で検証しています。5端末同時登録での採番重複なし、2端末同時での請求更新実行時にbilling_closings行が1件しか作られないこと（実際にロック競合のエラーが発生することも含めて）、確定済み伝票が編集・削除できないことを確認済みです

## CSVインポートについて

各マスタの一覧画面から「CSV取り込み」で、CSVファイルを一括登録・一括更新できます。

- 文字コードはUTF-8・Shift_JIS(CP932)のどちらでも自動判定します（Excelで保存したCSVでもそのまま使えます）
- 1行目は見出し行として扱い、旧システムのCSVエクスポートと同じ列名（得意先コード・得意先名称1 など）を認識します。列の順番は入れ替わっていても構いません
- 同じコードの行が既にある場合は上書き更新、無い場合は新規登録します（アップサート）
- 担当者コード・地区コードなど、参照先のマスタに存在しないコードが指定されていた場合は、その項目だけ空欄にして登録を続行します（行ごと失敗にはしません）。件数は結果画面に表示されます
- コード・名称など必須項目が空の行はスキップされ、結果画面にスキップ理由が表示されます
- 得意先の「請求先コード」は自己参照のため、全件登録後にまとめて設定されます

**列名の見出しが全角スペースを含む場合（商品マスタCSVの「商　品　名」「規　格」など）も、空白を除去して比較するため問題なく取り込めます。**

## セットアップ

### 1. 前提

- Node.js 20以上
- PostgreSQL 16（`schema.sql` を投入済みのデータベース）

### 2. 環境変数

`.env.example` を `.env` にコピーし、値を設定してください。

```bash
cp .env.example .env
```

- `DATABASE_URL` : 接続先のPostgreSQL（例: `postgresql://user:password@localhost:5432/arai_hanbai`）
- `AUTH_SECRET` : セッション署名用のランダム文字列。`openssl rand -base64 32` などで生成してください。

### 3. 依存関係のインストールとPrisma Client生成

```bash
npm install
npx prisma generate
```

データベースに `schema.sql` をまだ投入していない場合は先に投入し、その後 `npx prisma db pull` でPrismaのスキーマ定義を実データベースに同期してください（このリポジトリの `prisma/schema.prisma` は投入済みの状態から生成されています）。

### 4. 初期ユーザーの作成（開発用）

```bash
npx prisma db seed
```

ログインID `admin` / パスワード `changeme123` の管理者ユーザーが作成されます。**本番投入前に必ずパスワードを変更してください。**

### 5. 開発サーバー起動

```bash
npm run dev
```

http://localhost:3000 を開いてください。未ログイン時はすべてのページが `/login` にリダイレクトされます。

## ディレクトリ構成の要点

- `prisma/schema.prisma` : `schema.sql` を投入済みのDBから `prisma db pull` で生成したもの

- `src/middleware.ts` : 未ログイン時のリダイレクト
- `src/app/(protected)/` : ログイン後の画面（得意先・仕入先・商品マスタなど）
- `src/lib/actions/` : 各マスタのServer Actions（作成・更新・無効化）

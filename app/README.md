# 荒井機工 販売管理システム（アプリ）

Next.js（App Router）+ TypeScript + Prisma + Auth.js（NextAuth v5, Credentials認証）構成の業務アプリです。
データベース設計そのものは一つ上の階層の `schema.sql` / `README.md`（DB設計方針）を参照してください。

現時点で実装済みなのは、マスタ管理画面（得意先・仕入先・商品。一覧検索（`pg_trgm`によるあいまい検索対応）・新規登録・編集・無効化（論理削除）・CSV取り込み）、売上伝票・仕入伝票・入金伝票・支払伝票・見積書の入力画面（いずれも新規登録・編集・削除・一覧検索）、請求更新（締め処理）・仕入支払更新、商品受払台帳、そして各種帳票（請求書・納品書・見積書）のPDF出力です。

## 売上伝票について

- 担当者は、担当者コードを入力する欄です（一覧から選ぶこともでき、入力したコードの担当者名を下に表示します）。新規登録では、ログインしているユーザーに紐付いた担当者（ユーザー管理の「担当者（担当者マスタとのひも付け）」で管理者が設定）が最初から入ります。変えることもできます。担当者マスタに無いコードでは保存できません。編集では、無効にした担当者も一覧に「（無効）」と付けて表示します
- 明細の入力欄は、実際の伝票と同じく商品名の下に規格、備考は備考1・備考2の2段です（納品書にも上下2段で印刷します）
- 商品名・規格は、納品書に文字を小さくせずに印刷できる**半角32文字（全角は2文字分と数える）まで**しか入力できません。超えた分の文字は入りません（貼り付けた場合や、商品マスタから長い名前の商品を選んだ場合も32文字までにします。日本語入力の変換中は切らず、確定したときに切り詰めます）。入力欄は印刷と同じ等幅のフォント（BIZ UDゴシック。無ければMSゴシック）で、32文字がちょうど見える幅です。上限に達すると枠がオレンジ色になります（`src/components/PrintWidthInput.tsx`、上限は `src/lib/text-width.ts` の `DELIVERY_NOTE_NAME_MAX`。納品書の商品名の欄は半角33文字まで入ります）
- 一覧画面（`/sales-vouchers`）から新規登録・検索（伝票番号・得意先コード・得意先名・日付範囲）ができます
- 明細行は商品コード・商品名の部分一致（あいまい検索対応）で商品マスタから検索し選択できます。商品マスタに無い品名（値引きなど）は自由入力も可能です
- 数量はマイナス値を許容します（値引き・返品行なども1明細として表現できます）
- 消費税率は伝票日付をもとに `tax_rate_history` から自動判定されます（現行は2019/10/1以降10%）
- 金額の丸め方式は得意先マスタの `rounding_method`（四捨五入・切捨て・切上げ）に従います
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `sales`）
- 請求確定済み（`is_billed = true`）の伝票は編集・削除できません

## 明細の商品コード欄について（売上伝票・仕入伝票・見積書共通）

- 明細の先頭に「商品コード」欄があります。コードを入力してEnter（または次の欄へ移動）すると、商品マスタから品名・規格・単位・単価が入ります。F8キーで商品検索ダイアログを開けます
- 商品マスタに無いコードは「該当する商品なし」と表示され、そのままでは保存できません
- **手打ち用コード「1」**: 旧システムと同じく、マスタに無い品物は商品コード「1」を入力して品名を自由に入力します（商品マスタの「手打ち商品」は仮の名前で、明細には使いません）。品名は明細ごとに保存されます。コード「1」は商品受払台帳の対象外です
- 品名欄からの候補検索は、商品コードが空の行でのみ動きます。コードが入っている行では品名を書き換えてもコードは変わりません

## 仕入伝票について

- 一覧画面（`/purchase-vouchers`）から新規登録・検索（伝票番号・仕入先コード・仕入先名・日付範囲）ができます
- 明細の商品検索・自由入力・マイナス数量（返品など）は売上伝票と同様に使えます
- 売上伝票と異なり、明細は仕入単価・仕入金額のみです（売価は扱いません）。伝票全体では仕入金額（`subtotal_amount`）・消費税額・合計金額を管理します
- 消費税率・丸め方式の判定ロジックは売上伝票と共通です（丸め方式は仕入先マスタの `rounding_method` を参照）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `purchase`。売上伝票とは別の連番です）
- 支払更新済み（`is_settled = true`）の伝票は編集・削除できません

## 入金伝票について

- 一覧画面（`/receipt-vouchers`）から新規登録・検索（伝票番号・得意先コード・得意先名・日付範囲）ができます
- 入金明細は1伝票に複数行登録でき、行ごとに区分（現金・振込・手形・その他）と金額を入力します
- 区分が「振込」「手形」の行は振込先銀行（銀行マスタ `banks` から選択）を指定できます。「手形」の行はさらに手形決済日・手形Noを入力できます
- 請求金額・売上金額・消費税額は、請求更新（締め処理）が未実装のため、現時点では参考情報として手入力する項目です（旧システムの請求書と照合する際の控えとして利用してください）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `receipt`）
- 売上伝票・仕入伝票と異なり「確定状態」を表すフラグがスキーマ上存在しないため、入金伝票はいつでも編集・削除できます

## 支払伝票について

- 一覧画面（`/payment-vouchers`）から新規登録・検索（伝票番号・仕入先コード・仕入先名・日付範囲）ができます
- 入金伝票と同じ構成です（対象が得意先→仕入先に変わり、参考項目が「売上金額」→「仕入金額」になります）。区分（現金・振込・手形・その他）ごとに明細行を登録し、「振込」「手形」は支払元銀行を、「手形」はさらに手形決済日を指定できます
- 入金伝票の `bill_no`（手形No）に相当する項目はスキーマ上支払伝票には無いため、支払伝票の明細には手形Noの入力欄がありません
- 請求金額・仕入金額・消費税額は、請求更新（締め処理）が未実装のため参考情報として手入力する項目です
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `payment`）
- 入金伝票と同様、確定状態のフラグがないためいつでも編集・削除できます

## 見積書について

- 一覧画面（`/quotations`）から新規登録・検索（伝票番号・得意先コード・得意先名・案件名・見積日範囲）ができます
- ヘッダには案件名（2行）・納期・受渡場所・荷造運賃・支払条件・有効期限・参照番号・補助番号・相手先担当など、旧システムの見積書帳票に合わせた項目を用意しています
- 「階層タイプ」チェックボックスを入れると、明細行ごとに「明細行／見出し（大・中・小）」を選べるようになります。見出し行は品名テキストのみを持ち、金額の集計には含まれません（インデント表示されます）。チェックを外すと通常の明細のみの見積書になります
- 明細の商品検索は売上伝票・仕入伝票と同じ仕組みで、商品マスタに無い品名の自由入力にも対応しています
- 見積金額・原価金額・粗利額は明細行（見出し行を除く）の数量×単価から自動計算されます
- 「消費税を含めて計算する」はスキーマ上フラグのみを保持する項目で、実際の消費税額は計算・保存されません（旧システムの仕様を踏襲した表示用の設定です）
- 伝票番号は自動採番されます（`voucher_sequences` テーブルで管理、種別 `quotation`）。確定状態のフラグはないためいつでも編集・削除できます
- `quotation_lines.category`（区分）列は現状フォームに出していません（用途が明確になり次第、他マスタ同様に追加予定です）

## 請求更新（締め処理）について

売上伝票をもとに得意先ごとの請求額を確定させる処理です。旧システムの「請求更新」に相当します。

- `/billing-closings` から「新規実行」を選び、締日（5日・10日・15日・20日・25日・月末、またはすべての締日）と基準日（この日までの伝票を集計）を指定して「プレビュー」すると、対象になる得意先と金額の内訳が実行前に確認できます。内容を確認したうえで「この内容で請求更新を実行する」を押すと確定します
- 対象は、得意先マスタの「締日」（未設定の場合は会社設定の既定締日）が指定した締日と一致する得意先です。得意先の「請求先コード」で請求がまとめられている場合は、まとめ先の得意先の1件としてグループ集計されます（グループ内の各社の売上・入金を合算）
- 金額の計算式は「今回請求額 = 前回請求残 + 今回売上金額 + 消費税額 − 今回入金額」です。前回請求残は前回の請求更新（取り消されていないもの）の請求額を、それが無い場合は得意先マスタの「稼動時残高」を初期値として使います
- 今回売上金額の対象は、まだ請求更新されていない（`is_billed = false`）売上伝票のうち伝票日付が基準日以前のものすべてです。今回入金額の対象は、前回の請求更新の集計期間の翌日から基準日までに登録された入金伝票です
- 実行すると、対象の売上伝票はすべて「請求確定済み」（`is_billed = true`）になり、編集・削除ができなくなります
- 基準日が、その得意先の前回の請求更新（取り消されていないもの）の対象期間の終了日以前の場合は「締め済み」として対象外になり、プレビューに件数が表示されます。同じ締日・基準日で誤って2回実行しても、前回請求残だけの実績（同じ金額の請求書）が重複して作られることはありません。新しい売上が無くても前回請求残がある得意先は、次の期間の基準日で実行すれば従来どおり繰越の請求実績が作られます
- 実行履歴は一覧・詳細画面でいつでも確認できます。詳細画面の「この請求更新を取り消す」から取り消すと、対象の売上伝票は「未請求」に戻り、以後の請求更新で再度対象になります（取り消した履歴はレコードとして残ります）
- 対応するのは売上・請求（得意先向け）です。仕入・支払（仕入先向け）は「仕入支払更新」として別に用意しています

### 締め日を過ぎた伝票・取り消しのルール

- 売上伝票・入金伝票の入力画面では、伝票日付がその得意先の直近の締め日（締日と今日の日付から計算。例: 20日締めで今日が9/27なら9/20）以前の場合、「締め日を過ぎた期間の伝票」である旨の注意書きを表示します。入力・保存は止めません（直近の締めは取り消して直せる運用のため）。仕入伝票・支払伝票でも仕入先の締日で同様に表示します
- 請求更新（仕入支払更新）の取り消しは、各得意先（仕入先）の**一番新しいものからしかできません**。後の請求の「前回請求残」は前の請求額を引き継いでいるため、古いものだけを取り消すと残高の繰り越しが食い違うためです。古いものを取り消そうとすると「新しいものから順に取り消してください」と表示されます
- 修正の流れ: 直近の請求更新を取り消す → 売上伝票を修正 → 同じ締日・基準日で請求更新を実行し直す → 請求書を差し替える

## 仕入支払更新について

仕入伝票をもとに仕入先ごとの支払額を確定させる処理です。旧システムの「仕入支払更新」に相当し、請求更新（得意先向け）と対になる仕組みです。

- `/payment-closings` から「新規実行」を選び、締日と基準日を指定して「プレビュー」すると、対象になる仕入先と金額の内訳が実行前に確認できます。内容を確認したうえで「この内容で仕入支払更新を実行する」を押すと確定します
- 対象は、仕入先マスタの「締日」（未設定の場合は会社設定の既定締日）が指定した締日と一致する仕入先です。得意先の「請求先コード」のような請求先グループ化の仕組みは仕入先マスタには無いため、仕入先ごとに個別に集計されます
- 金額の計算式は「今回支払額 = 前回残高 + 今回仕入金額 + 消費税額 − 今回支払額（支払伝票分）」です。前回残高は前回の仕入支払更新（取り消されていないもの）の支払額を、それが無い場合は仕入先マスタの「稼動時残高」を初期値として使います
- 今回仕入金額の対象は、まだ仕入支払更新されていない（`is_settled = false`）仕入伝票のうち伝票日付が基準日以前のものすべてです。今回支払額（相殺分）の対象は、前回の仕入支払更新の集計期間の翌日から基準日までに登録された支払伝票です
- 実行すると、対象の仕入伝票はすべて「支払更新済み」（`is_settled = true`）になり、編集・削除ができなくなります
- 請求更新と同様に、基準日がその仕入先の前回の仕入支払更新の対象期間の終了日以前の場合は「締め済み」として対象外になります（同日の二重実行による支払額の二重計上を防ぐため）
- 実行履歴は一覧・詳細画面でいつでも確認できます。詳細画面の「この仕入支払更新を取り消す」から取り消すと、対象の仕入伝票は「未払」に戻ります（取り消した履歴はレコードとして残ります）

## 商品受払台帳について

商品ごとの入庫（仕入）・出庫（売上）の履歴と残数量・残高金額を確認できるレポート画面です。

- `/inventory-ledger` を開くと商品検索欄が表示されます。商品マスタは約14万6千件あるため、コードまたは商品名で絞り込んでから選択します
- 商品を選ぶと、その商品の売上伝票・仕入伝票の明細を日付順に並べた受払台帳が表示されます。期間（From/To）で絞り込むこともできます。期間のFromを指定した場合、それより前の全履歴を集計した「前期繰越」を先頭行に表示します
- 数量は仕入伝票の明細を入庫、売上伝票の明細を出庫として扱い、残数量は入庫−出庫の累計です。残高金額は仕入原価（`cost_amount`）ベースの累計です（売価ではなく原価で評価する、一般的な受払台帳の考え方です）
- スキーマ上の `inventory_movements` テーブル（受払ログ用）は現在使用していません。この画面は売上伝票・仕入伝票の明細から都度計算する方式のため、伝票を修正・削除すれば台帳の内容も自動的に反映されます
- 商品マスタの `stock_qty`（在庫数量）・`stock_amount`（在庫金額）は画面上部に参考表示していますが、旧システムからの移行時点で在庫数量が引き継がれていないため通常0のままです。この受払台帳の残高計算とは連動しません
- 対象は商品コードが明細に記録されている行のみです。値引き・自由入力行など商品コードの無い明細は集計対象外です

## 各種帳票（PDF出力）について

売上伝票・見積書・請求更新の実績それぞれの詳細画面に「プレビュー」と「印刷する」のボタンがあります。「プレビュー」は別タブでPDFを開きます（`Content-Disposition: inline`）。「印刷する」は事務所のプリンターの決まったカセットへ直接印刷します（次の「印刷（指定カセットへの直接印刷）について」を参照）。PDFを作る処理は `src/lib/print/`（delivery-note.ts・quotation.ts・invoice.ts）にあり、プレビューと直接印刷の両方で同じものを使います。

- **納品書**（`/sales-vouchers/[id]/print`）: 売上伝票の明細から生成します。顧客向け帳票のため、仕入原価・粗利など内部情報は含みません。A4用紙1枚の上半分に「納品書」、下半分に「納品書（控）」を同じ内容で印刷します。「納品書（控）」はお客様に受領印をもらって持ち帰る受領書を兼ねます。用紙は上下の間にミシン目が入った色付きの用紙で、罫線も含めてすべて印刷するため、各部の位置は実際の伝票（見本）を実測した寸法（mm）で固定し、上下の区切りがA4のちょうど半分（148.5mm）に来るようにしています。**用紙のミシン目の位置は、A4用紙の上端から148.5mm**です（2026年9月に実際の用紙で、区切りがミシン目に合うことを確認済み。`src/lib/print/delivery-note.ts` の `PERFORATION_MM`）。レイアウトを変えるときも、この位置に合わせてください（PDFは余白0で出力。印刷時は「実際のサイズ」「拡大縮小なし」で印刷してください）。
  - 日付は `2026/09/25` の形、数量は不要な小数点以下を付けず、単価は小数点以下2桁（`4,870.00`）で印刷します。得意先名の上に〒・住所を印刷します
  - 2026年10月の変更: 自社名などを上へ詰めて明細の行を高くし（1行10.2mm）、文字を見本より2ポイント大きくしました。列の幅は、項7・商品名／規格80・数量15・単位10・単価25・金額24・備考29mm です（`COLS`）。明細の枠の左右両端の縦の罫線は、旧伝票と同じく引きません。商品名と規格、備考1と備考2は、それぞれ行の上の段・下の段に固定して印刷します（規格や備考2が空でも、商品名・備考1は上の段）。日付・得意先・伝票番号の枠も、左右両端の縦の罫線を引きません。欄に収まらない長い文字や大きな金額は、その欄だけ文字を小さくします
  - 請求先（親の得意先）の消費税の計算方法が「請求書単位」（`calc_method = 0`）の場合は、消費税を請求書でまとめて計算するため、納品書の消費税の欄は空欄にし、合計＝小計とします。「明細単位」（`calc_method = 1`）の場合だけ伝票の消費税を記載します
  - 明細は1枚につき7品番までで、8品番目以降は同じ伝票番号のまま2枚目以降に続けて出力します（例: 9品番なら1枚目に1〜7品番目、2枚目に8〜9品番目）。小計・消費税・合計は最終ページだけに記載し、途中のページには「次の用紙に続く」と印刷します
- **見積書**（`/quotations/[id]/print`）: 見積書の明細から生成します。白紙に罫線も含めて印刷し、各部の位置は実際の見積書（見本）を実測した寸法で固定しています。原価・粗利は含みません。
  - 右上に No.（見積番号）と日付（`2026年 9月 25日` の形）、得意先名に「御中」、その下に先方担当者（「山岸課長 様」の形）、「御見積金額 ¥327,500-」、件名2行、受渡場所・支払条件・納期・荷造運賃・有効期限を印刷します
  - 自社の表記の下に押印用の枠を3つ印刷します（印鑑は手で押す運用のため）
  - 明細は1枚19行の固定枠で、商品名と規格を1つの欄に2行で印刷し、最後の明細の次の行に「※ 合 計 ※」と見積金額を印刷します。19行に収まらない場合は複数枚に分け、合計は最終ページに記載します。階層タイプの見出し行は商品名欄に見出しだけを印刷します
  - 下部に備考（2行まで）と、「※ 上記価格には消費税は含まれておりません」（入力画面の「消費税を含めて計算する」にチェックがある場合は「含まれております」。新規作成時はチェックなしで始まります）を印刷します
- **請求書**（`/billing-closings/[id]/records/[recordId]/print`）: 請求更新の実績（`billing_records`）1件から生成します。「今回売上明細」は、その請求グループ（請求先に紐づく子アカウントも含む）に属し、かつその実績の対象期間（`period_from`〜`period_to`）に該当する売上伝票を都度再集計したものです。これは請求更新の取り消し処理が対象伝票を再特定するのに使っているのと同じ絞り込み条件なので、中間テーブルを持たずに「この請求に何が含まれていたか」を後から正確に再現できます
- 会社情報（自社名・住所・電話・FAX・適格請求書発行事業者登録番号）は `company_settings` テーブル（管理者メニューの「自社情報」画面で変更できます）から、振込先情報は `banks` テーブルの `is_own_company = true` の行から取得して各PDFに印字します（振込先が未登録の場合は単に非表示になります）
- 得意先名のあとの敬称は、`customers.honorific` が数値コードで意味の対応表がスキーマ上どこにもない（既存のマスタ画面でも生の値をそのまま表示しているだけ）ため、PDFでは一律「御中」を付けています。実際の敬称ルールと異なる場合は個別に見直してください
- PDF生成は、サーバー上でPlaywright（Chromium）を都度起動してHTMLを印刷する方式です。納品書・見積書は、MSゴシックと同じく文字幅が一定のフォント「BIZ UDゴシック」（モリサワ。数字の0に斜線が入らない）で、数字・英字も含めて印刷します（本番は Dockerfile で `fonts-morisawa-bizud-gothic` を導入。無い環境ではIPAゴシックで印刷します。欄に収まらない長い文字は、その欄だけ自動で文字を小さくします）。日本語フォントが入っている環境が前提のため、本番環境に配置する際は `npx playwright install chromium` を実行してブラウザ本体を用意してください（`package.json` の `dependencies` に `playwright` を含めています）

## 印刷（指定カセットへの直接印刷）について

事務所のプリンター（Canon iR-ADV C3520III）は、カセットごとに用紙が決まっています（カセット1=A4普通紙、カセット2=A4請求書用帳票用紙、カセット3=A4納品書用帳票用紙、カセット4=A5普通紙）。ブラウザの印刷ではカセットを指定できないため、事務所のパソコン1台に「印刷係」のプログラムを入れ、そのパソコンが帳票ごとに決めたカセットから印刷します。

- **流れ**: 各画面の「印刷する」で印刷の依頼（`print_jobs`）を登録 → 印刷係が数秒おきにシステムへ依頼を取りに来て（`/api/print-agent/*`）、PDFを受け取り、SumatraPDF でカセットを指定して実寸（拡大縮小なし）で印刷 → 結果を報告します。印刷係がこちらへ取りに来るだけなので、社内のネットワークやプリンターを外部に公開する必要はありません。どのパソコン・スマホから依頼しても、印刷係のパソコンから印刷されます
- **画面**: 依頼したボタンの下に「印刷を依頼しました → 印刷中です → 印刷しました」と状況を表示します。印刷係が接続されていない間は「印刷待ち」と表示し、接続されると順に印刷されます。メニューの「印刷状況」で直近100件の依頼の状況を確認でき、印刷待ちのものは取り消せます
- **帳票ごとのカセット**（`print_trays`）: 初期値は納品書=カセット3、見積書=カセット1、請求書=カセット2。管理者は「印刷状況」画面で変更できます
- **印刷係の接続キー**（`print_agents`）: 管理者が「印刷状況」画面で発行します。キーはその場で1回だけ表示し、DBにはSHA-256のハッシュだけを保存します。パソコンを入れ替えたときは古いものを「無効にする」で止めます。1分以上接続が無い印刷係は「未接続」と表示します
- **二重印刷の防止**: 依頼の取り出しは `FOR UPDATE SKIP LOCKED` で1件ずつ行い、同じ依頼を二重に印刷しません。印刷中のまま10分以上完了の報告が無い依頼はエラーにします（自動で再印刷はしません。プリンターを確認してから再度「印刷する」を押してください）
- **印刷係のプログラム**: `public/print-agent/print-agent.ps1`（Windows標準のPowerShell 5.1で動作。「印刷状況」画面からダウンロードできます）。事務所のパソコンに SumatraPDF をインストールし、PowerShellを管理者として実行して `powershell -ExecutionPolicy Bypass -File .\print-agent.ps1 -Setup` を実行すると、接続キー・プリンター・カセットと給紙トレイの対応を順に設定し、サインイン時に自動で起動するよう登録します（タスク名 `AraiKikou-PrintAgent`）。給紙トレイは、プリンタードライバーの給紙トレイの一覧から番号で選びます。印刷の前に、設定した給紙トレイがプリンターにあるかを確認し、無ければ別のカセットから印刷してしまわないようエラーにします。設定をやり直すと、動いている印刷係は次の確認から新しい設定を使います。`-ListTrays` でプリンターの給紙トレイの名前を一覧できます。動作の記録は同じフォルダの `print-agent.log` に残ります
- **テーブルの追加**: 本番DBにはマイグレーションの仕組みが無いため、これらのテーブルはアプリの起動時に `src/instrumentation.ts` → `src/lib/schema-upgrades.ts` が「無ければ作る」形で自動で追加します。今後テーブルを追加するときも同じ場所に追記し、`schema.sql`・`prisma/schema.prisma` にも同じ内容を書いてください

## ユーザー管理・パスワード変更について

- **ユーザー管理**（管理者のみ、メニュー「ユーザー管理」、`/users`）: ログインするアカウントの一覧・追加・編集・パスワードの再設定・無効化ができます
  - 項目: ログインID（半角英数字と . _ -、登録後は変更不可）、表示名、権限、担当者（担当者マスタとのひも付け）、パスワード（8文字以上）
  - 権限: 「管理者」は全機能とユーザー管理・データ移行、「一般」はそれ以外の普段の業務の機能
  - 使わなくなったアカウントは無効化します（削除はできません）。無効化・権限の変更は、本人が再ログインしなくても次の画面操作から反映されます
  - 自分自身の無効化や、有効な管理者が1人もいなくなる変更（最後の管理者の無効化・一般への変更）はできません
  - パスワードを忘れたユーザーは、一覧の「パスワードを初期値に戻す」で初期パスワード（`changeme123`、`src/lib/initial-password.ts`）に戻せます。本人はそのパスワードでログインし、ホーム画面の警告から新しいパスワードに変更します
- **パスワード変更**（全員、画面右上の「パスワード変更」、`/account/password`）: 今のパスワードを入力して、自分のパスワードを変更します
- 初期設定のパスワード（`changeme123`）のままのユーザーでログインすると、ホーム画面に変更を促す警告が出ます

## 担当者マスタについて

- `/staff`（メニューの「担当者マスタ」）で担当者の一覧・新規登録・編集・無効化ができます
- 担当者コードは、得意先マスタや伝票のCSVに書かれているコードと同じ書き方で登録してください（旧システムの `1` なら `1`。`01` とは別のコードとして扱われます）
- 退職などで使わなくなった担当者は削除せず「無効化」します。過去の伝票・得意先には残ったまま、入力画面の担当者の選択肢から外れます
- 得意先・仕入先マスタのCSV取り込みでは、担当者マスタに無い担当者コードは空欄になります。担当者を登録してからCSVを取り込み直すと、得意先の担当者が入ります

## データ移行（旧システムの伝票の取り込み）について

メニューの「データ移行」（管理者のみ表示、`/data-migration`）から、旧システムの売上・仕入・入金伝票のCSVをまとめて取り込みます。1回だけ行う作業です。

- CSVの形式: 売上・仕入は「伝票日付,伝票番号,区分,得意先/仕入先コード,得意先/仕入先名,商品コード,商品名,規格,数量,単位,単価,金額,備考,担当者コード,担当者名,摘要名」の明細単位。入金は「伝票日付,伝票番号,得意先コード,得意先名,区分,金額,手数料,相殺,手形決済日,入金日付」の1伝票1行（金額が全額で、手数料・相殺はその内訳として明細に分けて登録）
- 「内容を確認」で件数・自動登録されるマスタ・得意先ごとの直近の請求（繰越残）を確認してから「この内容で取り込む」で登録します。1つのトランザクションで行い、途中で失敗した場合は何も登録されません。同じ伝票番号が既にある場合や、取り消し済みでない請求更新がある場合は取り込めません
- 売上: 各得意先の最初の売上がある締めから直近の締めまでの請求更新を再現します（前回請求残は稼動時残高＝通常0から）。直近の締めより後の伝票は未請求のまま取り込みます
- 仕入: 各仕入先の直近の締めまでを支払更新済みにします（支払伝票のデータが無いため、過去の仕入支払更新は再現しません）
- マスタに無い得意先・仕入先・商品は、伝票に書かれた名前で旧マスタ（無効）として自動登録します。担当者マスタに無い担当者は空欄になります
- 取り込み後は伝票番号の採番カウンタが取り込んだ番号の続きになります

### 売上伝票の備考（備考1・備考2）

旧システムのCSVの「備考」は、売上伝票の備考1と備考2を半角スペース1つでつなげた形で出力されています（例:「3/7特機生 川端様」→ 備考1「3/7特機生」・備考2「川端様」、「 川端様」→ 備考1は空・備考2「川端様」、「北村様 」→ 備考1「北村様」・備考2は空）。データ移行・日計伝票取込では、最初の半角スペースで備考1・備考2に分けて取り込みます（`splitSalesNote`。仕入伝票は備考が1つなのでそのまま）。そのため、伝票の取り込みではCSVの各欄の前後の空白を残して読み、各欄を読むときに空白を除いています。

2026年10月より前の取り込みでは、つなげた備考をそのまま備考1に入れていました。データ移行の画面の「売上伝票の備考を、備考1・備考2に分け直す」で、そのときの売上伝票のCSVをもう一度選ぶと、取り込んだあとに画面で書き換えられていない明細だけを分け直せます（`src/lib/migration/note-repair.ts`。伝票番号と明細の順番・商品名で突き合わせます。何度実行しても同じ結果になります）。

### 請求の消費税の計算方式

請求更新・仕入支払更新の消費税額は、得意先（仕入先）マスタの「計算方式」に従います。

- 0（請求単位・既定）: 締めた期間の売上（仕入）合計に税率を掛け、丸め方式で端数処理します。旧システムの請求額（＝入金額）はこの方式で1円単位まで一致することを実データで確認しています
- 1（明細単位）: 各伝票に保存されている消費税額を合計します

## 日計伝票のCSV取り込みについて

旧システムと並行して使う間、旧システムで入力した売上・仕入の伝票を、メニューの「日計伝票取込」から何度でも追加で取り込めます（`src/lib/migration/daily-import.ts`）。データ移行（1回だけの作業）とは別の機能で、請求更新の再現は行いません。

- CSVはデータ移行と同じ明細単位の形式（伝票日付, 伝票番号, 区分, 得意先/仕入先コード, 得意先/仕入先名, 商品コード, 商品名, 規格, 数量, 単位, 単価, 金額, 備考, 担当者コード, 担当者名, 摘要名）で、売上と仕入が1つのファイルに混ざっていて構いません
- 区分「売上」「売値」の行は売上伝票、「仕入」の行は仕入伝票になります。「摘要」（メモ行）などは、同じ伝票番号の売上・仕入の伝票に入ります。1枚の伝票に売上と仕入の行がある場合は、それぞれの伝票に分けます。メモ行だけの伝票は、コードが仕入先マスタにだけあれば仕入、得意先マスタにだけあれば売上、どちらとも決められなければ同じファイルの中で伝票番号が近い方の伝票にします
- 既に登録されている伝票番号は取り込みません。日付・得意先（仕入先）・金額・明細の行数が同じなら「取り込み済み」、違えば「内容が違う」として一覧に表示します（旧システムで直した伝票は、こちらの伝票を削除してから取り込み直します）。期間が重なったCSVを取り込んでも二重には登録されません
- 取り込んだ売上は未請求、仕入は未払として登録し、次回の請求更新・仕入支払更新の対象になります。締め済みの期間の日付の伝票は、次回の請求・支払に含まれる旨をプレビューに表示します。消費税は画面から入力したときと同じ計算（売上は明細ごと、仕入は伝票ごと）です
- マスタに無い得意先・仕入先・商品は、データ移行と同じく伝票に書かれた名前で旧マスタ（無効）として自動で登録します。得意先・仕入先コードは4桁、伝票番号は6桁にそろえます（Excelで先頭の0が消えた場合のため）
- 取り込みは1つのトランザクションで行い、途中で失敗した場合は何も登録しません。請求更新・仕入支払更新と同時には動かないようにしています。取り込んだ伝票番号の続きから、こちらの採番が進むようにします
- **並行運用中の伝票番号について**: 旧システムとこのシステムの両方で伝票を入力すると、同じ伝票番号が別々の伝票に付くことがあります（その場合は「内容が違う」として取り込まれません）。並行運用中は、どちらか一方で入力することをおすすめします

## 伝票検索について

メニューの「伝票検索」（`/voucher-search`）で、売上・仕入・入金・支払伝票と見積書をまとめて探せます（`src/lib/voucher-search.ts`）。

- **伝票の種類**: チェックボックスで選びます（複数可。最初は見積書以外に印が付いています）
- **得意先・仕入先**: コード（数字だけなら4桁にそろえます。`54` → `0054`）の一致か、名前の一部で探します
- **商品名・規格**: 明細の一部一致で探します。全角カナ・ひらがな・半角カナのどれで入力しても同じ結果になります（旧システムのデータは半角カナが多いため。`src/lib/kana.ts`）。入金・支払伝票には商品の明細が無いため、商品名・規格で探すときは対象外です
- **担当者**: 担当者コードの一致か、名前の一部で探します（入力欄から担当者の一覧を選ぶこともできます）。担当者があるのは売上・仕入伝票と見積書だけなので、担当者で探すときは入金・支払伝票は対象外です。伝票モードの表・伝票の表示・CSVにも担当者を出します
- **伝票番号**（一部一致）と**伝票日付の期間**でも絞り込めます
- **表示モード**: 検索ボタンの手前で「明細モード」（既定。明細を1行ずつ表示。商品名・規格で探したときは当てはまった明細だけ）と「伝票モード」（伝票を1行ずつ表示）を選びます。検索した後に切り替えると、同じ条件ですぐに表示し直します
- **出力方法**: 「画面に表示」か「CSVファイルに出力」（Excelで開けるBOM付きUTF-8、明細ごとに1行）を選びます
- **並べ替え**: 結果の見出し（伝票番号・日付・得意先・商品名・数量・金額）を押すと並べ替え、もう一度押すと逆順になります。最初は日付の新しい順です。商品名・得意先はふりがな順で、マスタの「ﾌﾘｶﾞﾅ」を使います（ふりがなが無い手打ちの商品などは名前で並べます）。同じ値の行は日付・伝票番号・行の順です
- **伝票の表示**: 明細（伝票モードでは伝票）の行を押すと、その伝票の内容（すべての明細・金額・消費税）を検索結果の上に重ねて表示します。「閉じる」（またはEsc）で検索結果に戻り、「詳細画面を開く」で伝票の画面に移ります。商品名・規格で探したときは、当てはまった明細を黄色で表示します
- 結果の上に、種類ごとの件数と合計金額を表示します。種類ごとに500件までを表示し、超えた場合は期間などで絞り込むよう表示します
- 検索条件はURLに入るので、ブラウザの「戻る」で前の検索結果に戻れます

今どの作業をしているかが一目でわかり、作業ミス（売上と仕入の取り違えなど）を減らせるよう、画面全体の背景色を作業ごとに変えています（入力欄や表の白い枠の外側に色が付きます）。一覧・入力・詳細・編集の画面は同じ作業として同じ色です。メニューの各項目にも同じ色を付けています（パソコンは項目の前の丸、スマホはボタンの色）。

## 同時アクセス（複数端末からの同時利用）について

複数のPCから同時にログインして同時にデータを処理するケースを想定し、以下の対策をしています。

- **セッション**: Auth.jsはJWTセッション（サーバー側にセッションストアを持たない方式）なので、複数端末からの同時ログインはそもそも制約なく動作します
- **伝票番号の採番**: `voucher_sequences` テーブルへの採番はDBトランザクション内の原子的なUPDATE（`increment`）で行っており、PostgreSQLの行ロックにより同時に採番しても重複しません（さらに`voucher_no`列にUNIQUE制約があるため、万一の場合もDBレベルで重複が拒否されます）。5端末から同時に伝票を登録して番号が重複しないことをスモークテストで確認済みです
- **伝票番号が衝突した場合の自動繰り上げ**: 旧システムでは、他端末との競合で番号が衝突しそうな場合は自動的に次の番号へ送って登録・印刷を継続する挙動だったとのことなので、同様の動きにしています。データ移行直後の採番カウンタと実データのズレや、手作業でのDB調整などにより、採番した番号がたまたま既存の伝票番号と衝突した場合、エラー画面を出さずに自動的に次の番号を採番し直して保存を続行します（`src/lib/voucher-number.ts` の `withVoucherNoRetry`、最大5回まで自動リトライ）。売上伝票・仕入伝票・入金伝票・支払伝票・見積書のすべての新規登録に適用しています。実装上の注意点として、採番のincrement処理は伝票本体の保存とは別にコミットするようにしています（同じDBトランザクションにまとめてしまうと、保存側が失敗した際にincrementまで巻き戻り、リトライしても同じ番号に衝突し続けてしまうため）。`scripts/smoke_voucher_number_retry.mjs` で、あらかじめ次の番号を使う伝票を仕込んだ状態から新規登録しても、その次の番号で自動的に登録が完了することを確認しています
- **採番カウンタと実データの同期**: 今回のデータ移行時点で `voucher_sequences`（売上伝票）のカウンタが実データの最大伝票番号より大幅に低い状態（カウンタ54に対し実データ最大144870）だったため、`scripts/sync_voucher_sequences.mjs` を実行し、各伝票種別のカウンタを実データの最大値まで引き上げました。このスクリプトは「カウンタが実データの最大値より小さい場合のみ引き上げる」という冪等な処理なので、何度実行しても安全です。将来、本番データへの本格的なカットオーバーを行う際は、同じスクリプトをもう一度実行してください（`node scripts/sync_voucher_sequences.mjs`）
- **請求更新・仕入支払更新の二重実行防止**: 「未請求（未払）データを集計→実績を作成→対象伝票を確定済みにする」処理はDBトランザクションでまとめていますが、PostgreSQLの既定の分離レベル（READ COMMITTED）では、2人がほぼ同時に「実行」を押すと同じ未処理データを両方が読んでしまい、二重請求・二重支払処理が起こり得ます。これを防ぐため、実行・取り消しのトランザクション冒頭で `pg_try_advisory_xact_lock` によるロックを取得し、同じ種類の締め処理はクラスタ全体で常に1件ずつ順番に処理されるようにしています。ロックが取得できなかった場合は「他の端末で同じ種類の締め処理を実行中です。少し待ってから、もう一度お試しください。」というエラーになります（`src/lib/closing-lock.ts`）
- **請求確定済み・支払確定済み伝票の編集/削除防止（TOCTOU対策）**: 伝票の編集・削除は、事前に確定状態を確認したうえで実行しますが、その確認と実際の更新/削除の間に別端末で請求更新・仕入支払更新が割り込む可能性があります。これを防ぐため、実際の更新・削除処理そのものに `is_billed: false` / `is_settled: false` の条件を含め、「未確定であることの確認」と「更新・削除」を1つの原子的なSQL文にまとめています。競合していた場合は「請求確定済みの伝票は編集できません（他の端末で先に請求更新された可能性があります）。」のようなエラーになります
- **DB接続プール**: 複数端末からの同時アクセスを想定し、`src/lib/prisma.ts` でPostgreSQL接続プールの上限を明示的に設定しています（既定20、`DATABASE_POOL_MAX` 環境変数で変更可能）
- これらは `scripts/smoke_concurrency.mjs` で検証しています。5端末同時登録での採番重複なし、2端末同時での請求更新実行時にbilling_closings行が1件しか作られないこと（実際にロック競合のエラーが発生することも含めて）、確定済み伝票が編集・削除できないことを確認済みです

## CSVインポートについて

各マスタの一覧画面から「CSV取り込み」で、CSVファイルを一括登録・一括更新できます。

- 文字コードはUTF-8・Shift_JIS(CP932)のどちらでも自動判定します（Excelで保存したCSVでもそのまま使えます）
- 1行目は見出し行として扱い、旧システムのCSVエクスポートと同じ列名（得意先コード・得意先名称1 など）を認識します。列の順番は入れ替わっていても構いません
- 同じコードの行が既にある場合は上書き更新、無い場合は新規登録します（アップサート）
- 担当者コード・地区コードなど、参照先のマスタに存在しないコードが指定されていた場合は、その項目だけ空欄にして登録を続行します（行ごと失敗にはしません）。件数は結果画面に表示されます
- コード・名称など必須項目が空の行はスキップされ、結果画面にスキップ理由が表示されます
- 得意先の「請求先コード」は自己参照のため、全件登録後にまとめて設定されます
- 得意先・仕入先のコード（請求先コードを含む）は4桁です。CSVをExcelで開いて保存すると先頭の0が消える（0006 → 6）ため、数字だけで4桁未満のコードは先頭に0を補って4桁にそろえて取り込みます（商品コードは対象外）。以前の取り込みで先頭の0が無いコードのまま別に登録されてしまった得意先・仕入先は、伝票などが紐づいていなければ取り込み時に自動で削除し、紐づいている場合は結果画面にコードを表示します
- 得意先・仕入先の取り込みでは、CSVに載っている得意先・仕入先を「有効」にします（データ移行で旧マスタ（無効）として自動登録されたものも、今のマスタに載っていれば有効に戻ります）

**列名の見出しが全角スペースを含む場合（商品マスタCSVの「商　品　名」「規　格」など）も、空白を除去して比較するため問題なく取り込めます。**

## セットアップ

### 1. 前提

- Node.js 20以上
- PostgreSQL 16（`schema.sql` を投入済みのデータベース）

### 2. 環境変数

`.env.example` を `.env` にコピーし、値を設定してください。

```bash
cp .env.example .env
```

- `DATABASE_URL` : 接続先のPostgreSQL（例: `postgresql://user:password@localhost:5432/arai_hanbai`）
- `AUTH_SECRET` : セッション署名用のランダム文字列。`openssl rand -base64 32` などで生成してください。

### 3. 依存関係のインストールとPrisma Client生成

```bash
npm install
npx prisma generate
```

データベースに `schema.sql` をまだ投入していない場合は先に投入し、その後 `npx prisma db pull` でPrismaのスキーマ定義を実データベースに同期してください（このリポジトリの `prisma/schema.prisma` は投入済みの状態から生成されています）。

### 4. 初期ユーザーの作成（開発用）

```bash
npx prisma db seed
```

ログインID `admin` / パスワード `changeme123` の管理者ユーザーが作成されます。**本番投入前に必ずパスワードを変更してください。**

### 5. 開発サーバー起動

```bash
npm run dev
```

http://localhost:3000 を開いてください。未ログイン時はすべてのページが `/login` にリダイレクトされます。
